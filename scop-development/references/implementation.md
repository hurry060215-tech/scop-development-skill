# Implementation, documentation, and assets

Apply these conventions to the authorized change, not as a reason to refactor unrelated files.

## APIs and code

- Search parameters and callers first. Reuse semantically matching names, values, defaults, and subset-selection conventions. Add parameters only when necessary and explain why; do not overload a different meaning or hide duplicate parameters in `...` or configuration lists. Update callers, help, and tests; preserve published compatibility.
- Follow local naming and S3/S4 dispatch. Name interfaces/results by purpose or method; avoid new implementation suffixes such as `cpp`, vague `dynamic`, and unnecessary package affixes. Preserve names required for compatibility or tooling; do not bulk-rename existing interfaces.
- Common entry points own shared validation, dispatch, and assembly; method interfaces own specialized logic. Centralize shared conversions and caches. Inline one-use thin helpers without an independent contract; meaningful algorithm stages, complex validation, and cleanup may remain functions.
- Keep R implementations in flat responsibility-based `R/` files. Group resource interfaces by source; do not create one file for each thin download, preparation, forwarding, or conversion helper. Preserve the one-method-per-file convention for independent public analysis methods.
- Prefer joint-column matching for compound identifiers. When a single key is necessary, use unambiguous encoding. Do not split naive concatenations or delimiter substitutions to recover original fields. Check delimiter-containing values, missing/empty values, and order-sensitive inputs.
- New data interfaces use `object` as the first argument. Migrate published `srt`/`bulk` interfaces only in an authorized API change; retain required aliases with default `NULL` and normalize once at entry. Do not add historical aliases to new APIs or rename parameters during unrelated repairs. Do not introduce mutually exclusive data-argument pairs.
- New public thread arguments use `cores`. When a published thread interface is intentionally migrated, deprecate and normalize required old names, and error when both old and new names are explicitly supplied; do not add compatibility branches without an actual supported caller. Assess internal budgets with `thisutils::detect_cores(max_threads = ...)`, after verifying its actual signature.
- Code-authored progress, success, warnings, and errors use `log_message()` with `message_type` and existing `verbose` control. Verify the actual logger signature: `verbose` controls ordinary messages only; errors terminate and warnings retain warning semantics even with `verbose = FALSE`. Do not directly emit these through `message()`, `warning()`, `stop()`, `cat()`, `print()`, another logger, or a per-method logging helper. Preserve dependency exceptions; never swallow errors or silently return to standardize output.
- Preserve existing startup messages in `*-package.R` and object/model printing and display methods (`print()`/`show()`); do not convert these to business logging.
- C++ and vendored code must not write directly to stdout/stderr. Only the R main thread may call `Rprintf()`/`REprintf()`; workers cache diagnostics for delivery on the main thread and never call any R API. Connect third-party headers through logging macros/callbacks and avoid direct platform `stderr` symbols in shared libraries.
- Ordinary analysis does not permanently modify session configuration. Restore temporary options and their originally unset state through `on.exit()`, including environment variables and `future::plan()`. Explicit initialization validates before modification. Do not add environment variables or hidden options to conceal failures.
- Define cache invalidation for asset versions, changed contents, additions, and removals. Construct sparse results directly when compatible with the algorithm; avoid an unnecessary dense `n × n` intermediate. Do not use `gc()` to conceal a structural problem.

## Keep defensive code proportional

- Validate external inputs at the owning public entry point or ingestion boundary. Internal helpers may rely on established invariants; do not repeat the same type, range, dependency, or shape checks at every layer. An independently callable public API still owns its boundary checks, and transformations that can invalidate an invariant require a relevant check.
- Keep checks that protect real contracts: required optional backends, supported input shapes, identifiers/cell order, safe object write-back, numerical preconditions, resource cleanup, and thread/runtime constraints. Simplification must preserve error/warning semantics and scientific correctness.
- Use the documented upstream API for the supported version range. Add version/signature branches only for an actual supported difference demonstrated by source, a caller, or a reproduced failure. Do not probe multiple guessed argument names, object fields, or package versions just in case.
- Let failures propagate unless handling provides necessary cleanup, actionable context, or an explicitly supported recovery. Avoid broad `tryCatch()` that returns `NULL`, empty results, zeros, or another method after failure. Do not silently drop observations, coerce invalid inputs, change algorithms, or switch backends to make execution succeed.
- Use existing shared helpers; inline one-off forwarding or conversion wrappers without their own contract. Do not introduce a generic adapter, configuration flag, readiness cache, or new abstraction for hypothetical future methods.
- In touched code, remove a defensive branch only after establishing that it is redundant, unreachable under the supported contract, or obsolete for supported callers. Validate the affected behavior. Do not turn a feature fix into a repository-wide cleanup or use line-count reduction as an acceptance target.

## Public documentation

- Document all exported public APIs in English. Use a concise action-oriented or method-name `@title` and a concise `@description` explaining purpose and relevant modes. One clear sentence is sufficient for a simple interface; add workflow context only when it helps users. Parameters specify types, enumerated values, valid ranges, and defaults; prefer `@inheritParams scop-params` for SCOP shared parameters when applicable. Provide complete help for exported APIs and retain shared parameter or conceptual topics such as `scop-params` when they serve real references. Do not add standalone help pages for internal helpers merely for uniformity.
- Use brief English source comments when they explain non-obvious algorithm choices, numerical stability, thread restrictions, or a verified compatibility constraint. Avoid comments that repeat the code, narrate edit history, or preserve dead code. Remove misleading/redundant comments only within scope; never delete useful rationale merely for uniformity. Preserve roxygen, copyright/license notices, and compilation/tool directives. Documentation-only work must leave function implementations unchanged.
- `@return` documents structure, matrix orientation, ordering, NA behavior, thresholds, and interval meaning. Do not fill API help with migration history, optimization claims, architecture, or manuscript background. Do not create help pages for internal helpers just to satisfy a template.
- State exact return types and dimensions. Object write-back help names the actual reduction/key, assay/layer, and metadata columns; plot/table help specifies types (such as ggplot, patchwork, HeatmapList, data.frame) and row/column statistical meaning. Add relevant upstream/downstream Markdown links in `@seealso`. Verify names against implementation rather than copying a template.
- Shared help owns the generic contract and supported categories/values. Put backend-specific settings, provenance, limitations, examples, and workflows in method/resource help, linked from the common entry point as needed. Avoid backend-specific details or return subsections in generic help. Reuse existing dispatch/traversal/assembly rather than duplicating the entry point or adding unnecessary restrictions for one category.
- Examples are short, representative, runnable, and free of private paths. Resource, query, and conversion interfaces do not need a full analysis chain. Keep large real-data validation outside the package. Preserve citations, copyright, licenses, and tool instructions.
- Use built-in data such as `pancreas_sub` (verify availability) or lightweight deterministic constructed data. No `library()`/`require()` or meaningless `if (file.exists(...))` wrappers. Protect heavy Python, unavailable optional dependencies, and network examples with `\dontrun{}`; this does not replace runtime dependency checks.
- For external algorithms with authoritative sources, optionally describe core steps using `\eqn{latex}{ascii}` or `\deqn{latex}{ascii}` and explain tuning parameters. Optionally cite author, year, title, journal, and `\doi{...}`. Verify formulas/citations against the method and implementation; do not invent them or copy an illustrative BANKSY formula as a verified contract. Engineering wrappers and methods without reliable sources need no forced formula/reference.
- Synchronize only task-required API docs, README, and website indexes. Inspect actual `_pkgdown.yml`, `DESCRIPTION`, and `.Rbuildignore` build behavior. Detailed usage belongs in function help.

## Repository assets

Restrictions follow purpose regardless of filename, location, extension, renaming, or repackaging.

- `inst/` contains only non-R-source resources needed after installation. Do not commit standalone demos, trial scripts, benchmarks, result capture/comparison scripts, or validation records. Usage goes in formal API examples/articles; temporary verification goes in an existing ignored or isolated directory.
- Formal unit tests use existing `tests/testthat/test-*.R`. Do not add loose testing scripts, testing manuals, fixtures, or test/demo/validation asset directories.
- No independent test data files: real, cropped, synthetic, serialized objects, CSV/TSV, JSON, images, or caches. Construct small deterministic inputs in code and assert necessary scalars or small structures. Do not evade the rule through large hard-coded arrays, encoded blobs, or generated files committed afterward.
- Run real-data and official-output comparisons in isolation; retain evidence outside the package distribution. Unit tests do not download assets or install dependencies. Explicitly skip ordinary tests missing optional dependencies (for example, `testthat::skip_if_not_installed()`). Such skips do not satisfy required backend acceptance in the designated prepared environment; see [validation.md](validation.md).
- `vignettes/` contains formal articles in the configured buildable format (SCOP currently uses `.Rmd`; verify the checkout) and index convention. Do not substitute plain `.md` articles. Reproduction, repair, review, and numerical acceptance records stay in isolation.

## SCOP method, resource, and plotting contracts

- Name independent analysis methods `Run<Method>` and keep one method per file. Prefer published or clearly peer-reviewed methods; document sources and implementation differences on the method page.
- Validate metadata, assay/layer, reduction names/keys, dimensions, and cell order before write-back. Never overwrite another method's results. Add `$summary` only as needed; reserve `$top_features` for feature rankings.
- Integrate databases/public resources through `PrepareDB()`. Use `mengxu98/datasets` mirrors or reliable official sources and existing local cache conventions. Data object names must not contain GEO accessions. Never add unauthorized data merely to make tests pass.
- Plotting starts with `object`; reuse `reduction`, `group.by`, `features`, `pt.size`, `palette`, and `theme_use` conventions. Use `DefaultReduction()` for automatic reduction selection, `patchwork::wrap_plots()` for combinations, and `thisplot::palette_colors()` for color mappings. Verify actual APIs before use.
